# Ranker R0 (PR 9, Phase A): lexical concept search on the tuning split

Status: Phase A only. R0 is round 0. It was measured once on the Riltra tuning split, against the
PR 8 baselines B1, B2 and B3 with the same frozen rules. The held-out split was not run. The result
applies to the **lexical ranker only**: edge expansion along proven edges (`via`) is deferred to a
separate PR after PR 9. Task 8 of the plan is not complete until that part is finished or the owner
cancels it, and nothing here claims otherwise. The agent block (PR 10) and the report (PR 11) are
later steps.

## R0 rules (frozen; changed only by the controller)

1. **Terms.** The whole text. Terms are the lowercase words that `concept::split_identifier`
   yields for every maximal run of non-whitespace characters, in order of first appearance and
   distinct. Words shorter than 3 characters and words made only of numeric characters (any script, `char::is_numeric`) are dropped. The first 64 are
   kept. No stoplist, no stemming, no prefix matching.
2. **Empty extraction.** No term: exit 0, `results: []`, `reason: "no-extractable-term"`.
3. **Match.** FTS5 over `concept_fts`, terms OR-joined and each double-quoted, restricted to the
   symbols of the pinned snapshot. The CLI and the MCP tool open the database with `store::open_read`
   (never `open_live`). Missing index: `no-index`. Older schema: `schema_outdated`. Newer schema:
   `schema_ahead`, which says to use a riltra binary that supports the database. Read error:
   `store_error`. One read transaction pins the snapshot, the freshness verdict, `total`, the rows
   and `why`.
4. **Order.** `bm25(concept_fts, 1.0, 1.0, 1.0)` ascending, then path ascending, then symbol start
   line ascending, then byte start. The score is not printed.
5. **Test demotion.** Unless a term is `test`, `tests`, `testing`, `spec` or `specs`: all non-test
   rows (`index::is_test_path` false) in rule-4 order, then all test rows in rule-4 order. Demotion
   acts before the candidate cap of rule 6. When a term names tests, the plain rule-4 order applies.
6. **Limit.** `--limit` defaults to 20 and must be 1 to 1000, else exit 2. `--text` must be
   non-empty and at most 16384 bytes, else exit 2 with a named cause. Candidates: each of the
   non-test and test lists keeps at most `CANDIDATE_CAP = 5000` rows (a `// shortcut:` comment
   marks it). `total` is an exact `COUNT`, and `truncated` is true when `total` exceeds the rows
   returned.
7. **Result row.** `path`, `line`, `name`, `kind`, `why`. `why` lists the query terms that FTS
   itself matched on that row, in query-term order (one `MATCH` per term, restricted to the
   returned rowids, in the same transaction).
8. **Document key order** (CLI and MCP print the same bytes):
   `repo`, `root`, `snapshot`, `freshness`, `reasons`, `terms`, `results`, `total`, `truncated`,
   `reason`, `basis`. `basis` is `"lexical-bm25-concept-fts"`. `reason` is `null` when rows exist,
   otherwise `no-index`, `no-match` or `no-extractable-term`.

## Measurement rules (harness)

- R uses B3's scratch index (no second build) and one `riltra query --limit 1000` call per task.
  Symbols collapse to files at their best rank and are restricted to the candidate universe.
- Statuses: `ok`, `index-failed` (same detail as B3 when the index was not built), `search-error`
  (non-zero exit, unparsable JSON, or an unexpected `reason`). A failure is never an empty list.
- `abstained`: status `ok` with `reason` `no-extractable-term`. Counted apart from failures.
- Pair verdicts keep the frozen `found@10` rule over tasks where both are `ok`.
- `name_hint` (descriptive heuristic, not a ceiling and not a bound): true when a gold path, or its
  lowercase stem, occurs in the lowercase query text. Git and the manifest only.
- The plan's ceiling ("tasks whose gold file is named nowhere in the text") is **deferred**. A
  sound version needs symbol names, which come from a parser, not from git.

## Results: Riltra tuning split

Run: `python -I docs/benchmarks/workflow/harness.py run --split tune` on `tasks-riltra.jsonl`
(manifest digest `84598bd71c1b6eef...`, rules `pr8-rules-1`, riltra version
`riltra 0.2.0-rc.1` built from this branch). Two runs produced byte-identical output (`cmp`).
Counts only. Sample: 81 tuning tasks (every task is `ok` for every baseline). 154 gold files are scored
across those tasks. No comparison or savings claim is made: a sample of 81 cannot support a threshold.

## Controls (controller, one-off, not part of the harness)

A text-free control on the same 81 tuning tasks ranks the files of the parent tree by size, largest first, and ignores the query. Tasks with at least one gold file in its top 5: 58; in its top 10: 71. R: 73 and 78; B1 37 and 38; B2 34 and 37; B3 21 and 23. The corpus is a small repository whose changed files are mostly its largest ones, so `found@10` is close to saturated and says little about ranking quality. R also returns many more files per task (median 19) than B1, B2 and B3 (median 1, 2 and 0), so the pair verdicts above compare a ranked list with short lists. The control was computed once with a local script that is not tracked; rerunning it needs the manifest and `git ls-tree -r -l` on each parent.

## Limits

- Sample sizes are small. No threshold, significance, comparison or savings claim is made.
- R returns at most 1000 symbols per task, from one call; further rows are unreachable.
- R is lexical: it follows no call edges and adds no `via`. Edge expansion is a separate later PR.
- Abstentions count as `ok` with no returned files, so they lower found@10 for R in pair verdicts.
- `name_hint` is a descriptive count only. It is not a bound on what any ranker can find.
- Phases B and C are not run here: no tuning round, and no held-out run.
