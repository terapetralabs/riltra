## R0 rules (frozen; changed only by the controller)

1. **Terms.** The whole text. Terms are the lowercase words that `concept::split_identifier`
   yields for every maximal run of non-whitespace characters, in order of first appearance and
   distinct. Words shorter than 3 characters and words made only of numeric characters (any script, `char::is_numeric`) are dropped. The first 64 are
   kept. No stoplist, no stemming, no prefix matching.
2. **Empty extraction.** No term: exit 0, `results: []`, `reason: "no-extractable-term"`.
3. **Match.** FTS5 over `concept_fts`, terms OR-joined and each double-quoted, restricted to the
   symbols of the pinned snapshot. The CLI and the MCP tool open the database with `store::open_read`
   (never `open_live`). Missing index: `no-index`. Older schema: `schema_outdated`. Newer schema:
   `schema_ahead`, which says to use a riltra binary that supports the database. Read error:
   `store_error`. One read transaction pins the snapshot, the freshness verdict, `total`, the rows
   and `why`.
4. **Order.** `bm25(concept_fts, 1.0, 1.0, 1.0)` ascending, then path ascending, then symbol start
   line ascending, then byte start. The score is not printed.
5. **Test demotion.** Unless a term is `test`, `tests`, `testing`, `spec` or `specs`: all non-test
   rows (`index::is_test_path` false) in rule-4 order, then all test rows in rule-4 order. Demotion
   acts before the candidate cap of rule 6. When a term names tests, the plain rule-4 order applies.
6. **Limit.** `--limit` defaults to 20 and must be 1 to 1000, else exit 2. `--text` must be
   non-empty and at most 16384 bytes, else exit 2 with a named cause. Candidates: each of the
   non-test and test lists keeps at most `CANDIDATE_CAP = 5000` rows (a `// shortcut:` comment
   marks it). `total` is an exact `COUNT`, and `truncated` is true when `total` exceeds the rows
   returned.
7. **Result row.** `path`, `line`, `name`, `kind`, `why`. `why` lists the query terms that FTS
   itself matched on that row, in query-term order (one `MATCH` per term, restricted to the
   returned rowids, in the same transaction).
8. **Document key order** (CLI and MCP print the same bytes):
   `repo`, `root`, `snapshot`, `freshness`, `reasons`, `terms`, `results`, `total`, `truncated`,
   `reason`, `basis`. `basis` is `"lexical-bm25-concept-fts"`. `reason` is `null` when rows exist,
   otherwise `no-index`, `no-match` or `no-extractable-term`.

## Measurement rules (harness)

- R uses B3's scratch index (no second build) and one `riltra query --limit 1000` call per task. Symbols collapse
  to files at their best rank and are restricted to the candidate universe.
- Statuses: `ok`, `index-failed` (same detail as B3 when the index was not built), `search-error` (non-zero exit,
  unparsable JSON, or an unexpected `reason`). A failure is never an empty list.
- `abstained`: status `ok` with `reason` `no-extractable-term`. Counted apart from failures.
- Pair verdicts keep the frozen `found@10` rule over tasks where both are `ok`. The pair `R-S` is added; no verdict rule is added.
- Mention class M1 (PR 9b; replaces `name_hint`): each task is `named`, `stem` or `none`, computed from git and the
  manifest only, over the gold files, never from Riltra output. `none` means "no mention that M1 accepts"; it is not
  "no gold file is named in the text". It is a descriptive class, not a ceiling and not a bound. The full rule and
  its limits are in the README of this folder.
- S control (PR 9b): the candidate universe ranked by blob size, largest first, ties by path ascending. It ignores
  the query and is always `ok`. It is a control, not a competitor.
- The plan's ceiling ("tasks whose gold file is named nowhere in the text") is **not measured**. M1 is the nearest
  descriptive class.

## Controls

S is now computed by the harness (`size_ranking` in `harness.py`), not by a local script; the PR 9 paragraph that
described an untracked script is replaced by it. Its counts agree with that earlier paragraph: S has at least one
gold file in the top 5 for 58 tasks and in the top 10 for 71; R 73 and 78; B1 37 and 38; B2 34 and 37; B3 21 and 23.
The corpus is a small repository whose changed files are mostly its largest ones, so S `found@10` is high and says
little about ranking quality. R also returns many more files per task (median 19) than B1, B2 and B3 (median 1, 2
and 0); S returns the whole candidate universe (median 24). The pair verdicts compare ranked lists of different
lengths.

## Limits

- Sample sizes are small: 3 `named`, 19 `stem` and 59 `none` tasks. No threshold, significance, comparison or
  savings claim is made.
- R returns at most 1000 symbols per task, from one call; further rows are unreachable.
- R is lexical: it follows no call edges and adds no `via`. Edge expansion is a separate later PR; Task 8 stays open.
- Abstentions count as `ok` with no returned files, so they lower found@10 for R in pair verdicts (none occurred here).
- M1 is descriptive; its limits are listed in the README. The PR 9 `name_hint` counts (31 true, 50 false) are
  replaced and are not comparable with the M1 classes.
- S is a control. A high S value does not say that a ranker is poor, and a low one does not say that it is good.
- Phase B was not run (no tuning round). Phase C, the one held-out run, is reported in `ranker-2026-11-heldout.md`.

## Query expansion (not measured)

Expansion along proven edges (`query --expand`) is implemented and tested on hand-built fixtures. Its effect on ranking is not measured: the benchmark repositories carry no SCIP import, so a benchmark run would add zero rows by construction. The R0 measurements above remain lexical-only records.
